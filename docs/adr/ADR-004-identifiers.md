# ADR-004: Internal identity keys, public UUIDv7

**Status:** Accepted · **Date:** 2026-09-24

## Context

The database wants small, dense, sequential keys. The outside world must not receive them. An order
at `/orders/1042` tells a competitor how many orders the store has taken, and invites anyone to try
`/orders/1041` to see whether the check is missing.

Random UUIDs as primary keys solve the leak and create another problem: every insert lands on a
random index page, so the index stops fitting in memory and writes slow down as the table grows.

## Decision

Three kinds of identifier, each with one job.

| Kind | Type | Used for |
|---|---|---|
| Internal | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Primary keys, foreign keys, joins |
| Public | `UUID` version 7 | URLs, API payloads, anything a client sees |
| Human | Sequence-backed string, e.g. `GS-2026-000123` | Order numbers, repair tickets, what a customer reads on the phone |

UUID version 7 (RFC 9562) starts with a 48-bit millisecond timestamp, so ids generated close in time
sort close together and keep the index dense. `PublicId.next()` generates them until PostgreSQL 18
brings the native `uuidv7()`.

## Consequences

- Every table a client can reach gets a `public_id UUID NOT NULL UNIQUE` column, filled by the
  application. Tables added from phase 2 onwards carry it from their first migration; the tables
  inherited from the demo get it when their module is rewritten.
- Controllers and DTOs accept and return the public id. The internal id never leaves the module.
- A public id leaks its creation time. That is acceptable for orders and products; anything where it
  is not gets a random identifier instead.
- Human-facing numbers are not identifiers: they are formatted, they may carry a check character, and
  they are never used as keys.
